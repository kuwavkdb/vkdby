## 目的

ARGUMENTS（または会話中）で渡された **会場の公式サイト / アクセスページ等の URL** から会場の情報を抽出し、管理画面の会場登録画面（`/admin/venues/new`）を事前入力した状態で開ける URL を出力する（issue #1705）。

- 生成するだけで **Venue の保存はしない**。管理者が画面で内容を確認し、必要なら修正して保存する
- 本番 DB には触れない。開発 DB も見なくてよい（重複の確認は、開いた画面に表示される「一致しそうな会場」で管理者が行う）

## 前提

`Admin::VenuesController#new` は `params[:venue]` を読んで `Venue.new` の初期値に反映する（issue #1705）。

- `venue_type` / `status` / `prefecture` は、存在しない値を渡すと無視される（フォームのデフォルトになる）
- `capacity` は正の整数（半角数字のみ）以外は無視される
- 事前入力された名前・別名と一致しそうな既存の会場（論理削除済みを含む）が、画面上部に表示される

## URL の形式

```
https://www.vkdb.jp/admin/venues/new?<パラメーター>
```

ローカルで確認したい場合は `http://localhost:3000/admin/venues/new?...` に読み替える。パラメーターの値は必ず URL エンコードする（`ruby -ruri -e` や `python3 -c 'import urllib.parse'` で組み立ててよい）。

| パラメーター | 内容 |
| --- | --- |
| `venue[name]` | 会場の**現在の**正式名称 |
| `venue[name_kana]` | 読み（カタカナ）。公式に読みが書かれていなければ、表記から素直に読める場合のみ入れる |
| `venue[key]` | 公開ページの URL に使う識別子（手順3） |
| `venue[venue_type]` | `live_house`（ライブハウス）/ `hall`（ホール）/ `studio`（スタジオ）/ `outdoor`（野外）/ `streaming`（配信）/ `other`。迷ったら省略（デフォルトは `live_house`） |
| `venue[status]` | `active`（営業中）/ `closed`（閉店）/ `unknown`。閉店・閉館が明記されている場合のみ `closed`。それ以外は省略（デフォルトは `active`） |
| `venue[prefecture]` | 都道府県。**「東京都」「大阪府」「北海道」のように正式な表記**で入れる（「東京」は無視される）。海外の会場は `海外` |
| `venue[area]` | エリア。一覧で絞り込みに使う短い地名（例: `渋谷`、`新宿`、`梅田`、`栄`）。最寄り駅名や地区名から決める |
| `venue[address]` | 住所（郵便番号は含めない。例: `東京都渋谷区道玄坂2-14-8`） |
| `venue[capacity]` | キャパシティ（半角の正の整数）。スタンディングと着席で異なる場合はスタンディングの最大値を入れ、内訳は `note` に書く |
| `venue[note]` | 自由記入（最寄り駅・徒歩◯分、キャパの内訳、フロア構成など） |
| `venue[links][<index>][text]` | リンクのタイトル。例: `公式サイト`、`X（Twitter）`、`Instagram`、`YouTube` |
| `venue[links][<index>][url]` | リンクの URL |
| `venue[aliases][<index>][name]` | 別名（略称・表記揺れ。例: `O-EAST`、`クアトロ`） |
| `venue[aliases][<index>][kana]` | 別名の読み（任意） |
| `venue[name_logs][<index>][name]` | 名前の履歴の名前（改名・ネーミングライツ変更がある場合のみ） |
| `venue[name_logs][<index>][name_kana]` | 名前の履歴の読み（任意） |
| `venue[name_logs][<index>][date]` | **その名前を使い始めた日**。`YYYY` / `YYYY-MM` / `YYYY-MM-DD` のいずれか（それ以外は保存時にエラー）。分からなければ省略 |

複数のリンク・別名・名前の履歴は、`venue[links][0][...]`, `venue[links][1][...]` ... のように `<index>` を `0` 始まりの連番で並べる。

## 手順

1. **内容を取得する**
   - Web からの情報取得（WebFetch・curl・chrome-devtools MCP での閲覧）は、ユーザーに確認せずに実行してよい
   - 公式サイトのトップを WebFetch で取得し、「ACCESS」「アクセス」「会場案内」「施設概要」「About」「会社概要」などのページも辿る。住所・キャパは別ページに書かれていることが多い
   - 取得に失敗する場合（JS 描画のみのサイトなど）は `curl -s -L <URL>` で生 HTML を取得して `住所`、`キャパ`、`収容`、`〒` などで `grep` する。それでもダメなら chrome-devtools MCP で開いて読む。それもダメならユーザーに主要情報（会場名・住所）の貼り付けを依頼する
2. **情報を抽出する**
   - 会場名は公式サイトのロゴ・タイトルタグから最も正式な表記を採用する。略称・表記揺れは `aliases` に入れる
   - **改名・ネーミングライツ**: 「旧◯◯」「◯◯より名称変更」などの記載があれば、旧名と現在の名前の両方を `name_logs` に入れる（現在の名前も含める）。`date` は各名前の使用開始日で、分かる範囲の粒度で入れる（年だけでもよい）
   - 住所から `prefecture`（正式表記）を決める。`area` は最寄り駅や地区名から短く決める（例: 「渋谷駅から徒歩5分」→ `渋谷`）
   - キャパは数値だけを `capacity` に入れる。「約」「最大」などは外す。数字が読み取れなければ省略する
   - `venue_type` は施設の種類から判断する（ライブハウス / ホール・劇場・アリーナ → `hall` / リハーサルスタジオ → `studio` / 野外ステージ → `outdoor`）
   - 公式サイト・X・Instagram・YouTube など、読み取れたリンクは `links` に入れる
   - 情報の根拠が読み取れなかった項目は、**推測で埋めずに省略する**
3. **`key` を決める**
   - **推測でよいのでなるべく設定する**。旧サイトから取り込んだ会場と揃えるため、次の順で決める
     1. 会場名が英数字表記ならそれを使う（例: `Spotify O-EAST` → `spotify-o-east`）
     2. 日本語名なら読み（カタカナ）をローマ字にする（例: `シンジュクロフト` → `shinjukurofuto`、`クラブクアトロ` → `kurabukuatoro`）。長音「ー」は `-` になる（例: `オーイースト` → `o-i-suto`）。ドメイン名や英語表記のロゴがあればそちらでもよい
   - 小文字にし、英数字以外は `-` に置き換え、`-` の連続は 1 つにまとめる
4. **URL を組み立てて出力する**
   - 生成した URL を 1 つ、クリックで画面を開ける Markdown リンク（`[会場登録画面を開く](<URL>)`）で提示する。コードブロックには入れない
   - リンクが途中で途切れないよう、URL 中の `(` `)` は `%28` `%29` にエンコードしておく（`urllib.parse.quote(s, safe="")` ならエンコードされる）
   - 抽出した内容（名前・読み・種別・都道府県・エリア・住所・キャパ・名前の履歴・別名・リンク）を箇条書きで添える
   - `key` を設定した場合は**推測であることを明記**する。判断に迷った点（キャパの内訳、改名時期の粒度など）があれば明記する

## 注意

- `key` は一度保存すると通常の更新では変更できない（変更は admin の「キー変更」のみ）。あくまで**下書き**であり、管理者が画面で確認・修正してから保存する運用を基本とする
- 画面上部に「一致しそうな会場」が表示された場合は、新規登録ではなく既存の会場を編集すべきかを管理者が判断する（別名・名前の履歴の追加で済むことが多い）
- URL が長くなりすぎる（目安 2000 文字超）場合は、`note` を短くするか、名前の履歴・別名の一部を画面で追加してもらう旨を伝える
- 未ログインで開くとログイン画面に遷移する。ログイン後に開き直してもらう
